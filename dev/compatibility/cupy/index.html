CuPy¶

CuPy is Advect's designated single-device GPU provider for the Array API frontend. Pass CuPy arrays to a transform and write numerical code against the traced array's namespace; the built-in compatibility fallback routes execution through CuPy while derivative seeds, temporaries, and captured constants stay on the device.

The configurations below are source records. A clean-worktree local run covers all three revisions, but no immutable artifact URL is published, so it does not verify a release CuPy support claim. Run the gate on the final candidate and retain its complete evidence before publishing one.

This is an Array API provider contract, not interception of arbitrary cupy.* calls. The function spellings below are methods of the namespace returned by a traced array.

A verified provider qualification would compose one retained configuration-level artifact with the runtime-derived Array API contract. It does not require a second CuPy-specific callable inventory.

The GPU gate below is a representative end-to-end workload rather than one GPU case per table row. It checks dynamic value/gradient, JVP, VJP, staged and serialized derivatives, FFT, linalg.solve, captured host constants, copied-field mutation, weak scalars, dtype/device retention, and cross-provider numerical agreement. The separate donation gate checks device-memory savings and runtime acceptance.

The mode columns are public support claims: yes means the callable's declared contract is supported end to end in that execution mode (dynamic tracing, abstract staging, serialized artifacts). Restricted implementation paths may remain internal, but registration alone does not promote an additional upstream spelling into this catalog.

Abstract=yes means that a primitive has a standalone abstract rule. A frontend may still be staged by an explicit method or composite lowering when its displayed primitive does not.

Install¶

Install the CuPy wheel family matching the CUDA generation available to the host. The configurations above used uv pip install 'cupy-cuda13x[ctk]==<version>'; the ctk extra made the toolkit libraries visible inside each isolated environment. Advect does not select the CUDA package, and no Advect extra or registration import is required.

Qualification gate¶

NumPy and array-api-strict run in automated CI. CuPy uses the same scientific provider workload on a CUDA host, followed by the staged donation acceptance gate. Run this once in each isolated environment containing the CuPy version being qualified:

uv run pytest \
  packages/advect/tests/advect_array_api_compat_tests/test_cupy_qualification.py

for version in 2022.12 2023.12 2024.12; do
  uv run python -m scripts.qualify_array_providers \
    --array-api-version "$version" \
    --providers numpy,array-api-strict,cupy \
    --output "artifacts/qualification/$version/array-provider-cupy.json"
done

ADVECT_SOURCE_REVISION="$(git rev-parse HEAD)" \
uv run python -m scripts.bench_runtime_memory \
  --profile cupy-donation \
  --acceptance \
  --format json \
  --output "artifacts/benchmarks/runtime-memory-cupy-donation.json"

The complete procedure, including donation evidence, lives in the provider qualification record.

Boundaries¶

  • One process and one device; multi-GPU placement and stream control are not claimed.
  • Arrays attached to another autodiff system (requires_grad=True) are rejected instead of composing two derivative tapes.
  • Other GPU providers may resolve through the same compatibility path; that behavior is incidental until the provider passes the same gate.
